**冲突 1 处：`src/components/member/MemberUpcoming.tsx`。** 值得记录，因为两边动的是同一件事：

- PR #41 修的浏览器报错 `Encountered two children with the same key, M4`，
  根因**正是本模块引入的** —— 通知与收藏两项的 `module` 都是 `"M4"`，而当时 key 取了 `module.module`。
- 但 PR #41 同时新增了单测 `tests/unit/m3-member-upcoming.test.ts`，断言
  `buildUpcomingEntries()` 返回 3 条（`notifications` / `favorites` / `ranking`）；
  而本模块已把通知与收藏换成真实摘要，该函数签名不再成立。

解决方式：

1. 保留本模块的真实摘要结构（通知 / 收藏各自用数据行 `id` 当 key，接入位只剩排行一项）；
2. 把「key 取能力标识而非 `module` 值」这条不变量拆成可测的纯函数，
   移到 `src/features/member-dashboard/upcoming-entries.ts`，并据此收窄上游单测；
3. **删除**本模块原先为消掉「`ranking` 未使用」而加的
   `<span className="sr-only">{ranking.module}</span>` —— 它把内部里程碑编号交给读屏软件，
   与上游「不把 `module` 渲染给终端用户」的约定冲突。抽出纯函数后 `ranking` 有真实用处，无需该元素。

> 为什么拆成单独文件而不是留在组件里：本仓库测试用 `tsx --test`，JSX 按经典运行时编译，
> 而 `Icon.tsx` 在模块顶层就求值 JSX；只要测试 import 组件，就会顺着
> `Button` → `Icon` 抛 `React is not defined`。纯逻辑必须放在与 JSX 无关的 `.ts` 模块中才可测。

同时修正了 `tests/integration/m4-community.test.ts` 的 5 处类型错误（`ae8f821`）：

## 已实现范围

### 评论与回复

- 维修详情页评论入口：根评论 + 直接回复；对回复再回复时服务端把 `parentCommentId`
  拍平到根，UI 仍在正文前缀 `@原作者`。
- 分页按根评论计，回复随当前页根评论一次带出。
- 正文拒绝空内容、超过 2000 码点、以及 TAB/LF/CR 以外的 C0 控制字符。
- `@` 解析按最长姓名匹配（昵称 / 实名 / 账号展示名），与显式
  `mentionedMemberProfileIds` 并集；未知显式 ID 拒绝，超限拒绝不截断。
- 作者可删自己的评论；删除他人评论需 `comment:delete`。软删除并写审计。

### 通知

- 类型：`MENTIONED`、`REPAIR_COMMENTED`、`REPAIR_APPROVED`、`REPAIR_REJECTED`。
- 不通知自己；同一评论对记录主人若同时被 @，只发 `MENTIONED`。
- 审核通知在审核事务内写入；审核员没有成员档案时仍通知记录主人。
- 标已读幂等；全部已读只更新未读行；删除走软删除且保留状态。

### 收藏与案例标记

- 收藏唯一约束 `(memberProfileId, repairRecordId)`；取消软删除，再次收藏恢复同一行
  并刷新时间。
- 疑难 / 典型案例复用 M2 的 `RepairRecord.isDifficult` / `isTypical` 与
  `PATCH /api/v1/admin/repairs/:id/flags`；成员详情展示徽章，管理员可改标记。

### 工作台与页面

- `GET /api/v1/member/dashboard` 的 `notifications` / `favorites` 为真实摘要；
  `ranking` 仍为 `{ available: false, module: "M5" }`。
- `degraded` 新增 `notifications` | `favorites`；M4 失败只降级对应区块。
- 页面：`/member/notifications`、`/member/favorites`；详情页评论 / 收藏 / 标记。
- 快捷操作增加通知与收藏入口。文案来自 `src/config/community.ts`。

## 数据、安全与隐私

- 业务外键一律指向 `member_profiles.id` / `repair_records.id`，QQ / 手机号 / 学号
  不进入 M4 表或列表字段。
- 评论、收藏可见性继承维修记录对象级权限；他人草稿统一 `REPAIR_NOT_FOUND`。
- 通知只能由收件人本人读取、标已读或软删除；他人 ID 一律 `NOTIFICATION_NOT_FOUND`。
- 评论创建 / 删除、收藏增减写 `AuditLog`，与业务行同事务。
- 默认查询排除 `deleted_at IS NOT NULL`。

### 本次修掉的真实缺陷：M4 集成测试 fixture 清理顺序

`tests/integration/m4-community.test.ts` 的 `prepareFixtures()` 里，`repairComment.deleteMany()`
按 `realName` 前缀直接删评论。但 `repair_comments` 有**自引用外键**（回复 → 根评论，
`onDelete: Restrict`），而 InnoDB 外键是**逐行即时检查**、没有 deferred 约束 —— 删到根评论时
子回复仍指向它，遂抛 `Foreign key constraint violated on the fields: ('parent_comment_id')`，
被 `beforeEach` 放大成 7/8 用例失败。

修复：清理时先把范围内回复拍平（`parent_comment_id` 置空，字段本就可空），再整批删除。
该缺陷**与数据库产品无关**，在 GreatSQL 上同样会触发 —— 集成用例此前从未执行过，所以一直未暴露。
